# devrestore — копия прода Битрикс для разработки и ИИ, с обезличиванием

Один файл `devrestore.php`. Кладётся в корень сайта рядом с архивом резервной копии и открывается в браузере. Восстанавливает копию через штатный `restore.php`, обезличивает персональные данные, отключает всё, что может уйти наружу, настраивает сайт под dev и прогоняет скрипты клиента.

## Как пользоваться

0. Один раз на машину: должна существовать папка профилей (см. ниже). Сам скрипт её не создаёт: её наличие и есть разрешение запуска на этой машине. Если файл случайно уедет на прод вместе с корнем сайта, там он ничего не сделает.
1. Положите в корень сайта архив копии и `devrestore.php`.
2. Откройте `http://<сайт>/devrestore.php`, в блоке «1. Восстановить свежую копию» введите домен и нажмите кнопку. Скрипт:
   - удалит старые архивы и дампы, чтобы restore.php не взял не тот;
   - скачает свежий `restore.php` и встроит в него три вещи: выключает его самообновление (иначе при первом открытии он скачивает себя с сайта Битрикс заново и молча стирает остальные вставки), сразу после импорта базы отключает агенты, очередь писем, вебхуки и почтовые ящики (на тестовом сервере с кроном иначе успели бы уйти письма из очереди прода), а на последнем шаге возвращает в devrestore. Если встроить не удалось (Битрикс поменял restore.php), подготовка отказывает, ничего не трогая. Записанный файл перечитывается: без вставок он удаляется. Если в корне лежит `restore.php` без вставок, главная показывает красное предупреждение — открывать его напрямую нельзя, подготовьте заново;
   - сохранит ключ `delight.mcp` из текущей базы;
   - если нашёлся клиент mysql, встроит в restore.php четвёртую вставку: после распаковки дамп грузит devrestore (см. «Быстрый импорт»).
3. Восстановите копию в restore.php как обычно. С быстрым импортом restore.php только распакует архив и передаст дамп devrestore: страница импорта покажет ход и сама перейдёт к обработке. Без него на последнем экране restore.php нажмите кнопку удаления файлов — вы вернётесь в devrestore.
4. Дальше зависит от клиента:
   - **знакомый клиент** — обработка стартует сама с запомненными настройками;
   - **новый клиент** — выберите скрипты и режим, и они запомнятся по боевому домену.
5. В конце вы увидите отчёт, логин и пароль dev-админа и результат проверки на утечки. Отчёт показывает время по этапам (импорт, обезличивание, проверка, уборка) и пять самых долгих шагов. Пароль показывается один раз и нигде не сохраняется. Постоянный пароль можно задать в `config.php`. Вход и cookie прежней копии к этому моменту сброшены (см. «Сброс входа»), поэтому войдите заново кнопкой «Войти на портал».

Если какой-то шаг обезличивания упал, отметка в базе это помнит: главная покажет базу красным «С ОШИБКАМИ», а не «обезличена».

Базу, восстановленную без devrestore, можно обработать с главной страницы: блок «Обработать текущую базу».

## Быстрый импорт

restore.php грузит дамп через веб-запросы короткими шагами — на базе в несколько гигабайт это десятки минут. Если на машине есть клиент mysql, дамп грузит он, а restore.php только распаковывает архив.

- **Где ищется клиент:** `mysql_bin` в `config.php`, затем `bin/` рядом с сервером MySQL (`@@basedir`), затем `PATH`; подходит и `mariadb`. Для фонового процесса нужен PHP для командной строки с mysqli — `php_bin`, рядом с PHP веб-сервера (`php-fpm` → `php`) или в `PATH`. Не нашлось — форма подготовки называет причину, и дамп по-старому грузит restore.php. `'mysql_bin' => false` выключает быстрый импорт совсем, галка в форме — на один раз.
- **Как идёт:** шаг 3 restore.php (после распаковки, с уже записанными настройками подключения) отправляет на страницу импорта devrestore. Она запускает в фоне `php devrestore.php --dr-import=<токен>`, тот читает дамп потоком, включая тома `.sql.1`, `.sql.2`…, и отдаёт его клиенту mysql. Как и в restore.php: выполняется `_after_connect.sql`, выключены проверки внешних ключей, `sql_mode` пустой, повтор строки (ошибка дубля) пропускается. Проверка уникальности не выключается: с ней выключенной MariaDB при повторе строки в дампе молча теряет строки, а MySQL может пропустить дубли в уникальный индекс.
- **Пароль базы** клиент получает из временного файла параметров (`--defaults-extra-file`, права 0600) в `state/`. Файл удаляется, как только клиент ответил на первый запрос.
- **Агенты и почта** отключаются по ходу импорта: как только в дампе кончились строки таблицы агентов (опций, очереди писем, вебхуков, почтовых ящиков), процесс отключает её, не дожидаясь остального дампа. После импорта всё отключается ещё раз. Если импорт упал или процесс убит, отключение тоже выполняется — процессом или страницей импорта. Там же делается то, что шаг 4 restore.php делает для копии на другом хосте: сброс корня сайтов, выключение CDN Битрикс, снятие ограничения хостов.
- **Второй запуск невозможен:** процесс держит блокировку. Страницу импорта можно закрыть и открыть заново по той же ссылке. Если процесс упал, она покажет ошибку и кнопку «Начать импорт заново». Обработка, пока импорт не закончен, не начинается — ссылка возвращает на импорт.
- **Пропуск данных** (`import_skip_truncated`, по умолчанию включён, галка в форме): строки таблиц, которые обработка всё равно очищает целиком (логи, поисковые индексы, сессии, корзина…), не загружаются, структура таблиц создаётся. Список берётся из тех же правил, группы, выключенные по умолчанию, не пропускаются.
- **Отчёт:** способ импорта, время, размер дампа и число томов, сколько данных пропущено. Для restore.php — время от подготовки до возврата и почему не клиентом mysql.

## Что делает обработка (по порядку)

| Шаг | Что |
| --- | --- |
| Отключение | агенты и `check_agents`, очередь писем `b_event`, заглушка `custom_mail` в `dbconn.php` (письма пишутся в `bitrix/php_interface/devrestore-mail.log`), SMTP, сетевой кеш, сессии и push-сервер прода в `.settings.php`, push-каналы, REST-вебхуки, почтовые ящики, коннекторы открытых линий, SMS-провайдеры, ключи облачных хранилищ, секреты в опциях и колонках `*PASSWORD/*TOKEN/*SECRET…`, сессии и 2FA, токены CalDAV (`b_dav_tokens`) и блокировки документов Диска. Отдельная группа, по умолчанию выключенная: автозапуск бизнес-процессов (там вебхуки в действиях) |
| Обезличивание | пользователи, CRM (контакты, компании, лиды, сделки, предложения, смарт-процессы, средства связи, реквизиты, адреса, дела, таймлайн, заметки, история), чаты и открытые линии, письма, телефония и SMS, живая лента, форумы, блоги, задачи (с чек-листами, результатами и историей изменений), календарь, журнал и задания бизнес-процессов, магазин, веб-формы, имена файлов, личные хранилища Диска, отчёты, рабочие отчёты, история ИИ, рассылки, подписание, пользовательские поля по типу и коду (CRM, RPA, пользователи), поисковые индексы, логи. Очищаются целиком: корзина и таблицы смарт-процессов, тип которых удалён |
| Отметка | опция `devrestore/info`: когда, чем, с каким боевым доменом, режим текста и число предупреждений проверки. Если в базе остались временные таблицы `zz_devrestore_*`, отметка не ставится |
| Dev-настройки | домен основного сайта, `server_name`, `cookie_name`, `site_name = DEV …`, «установка для разработки», новый `server_uniq_id` (сессии прежней копии недействительны) |
| Уборка | кеш, а также архив, дампы и restore.php (галка) |
| Ядро | модули разработки (`delight.mcp` с прежним `jwt_secret_key` — токен в `.mcp.json` продолжает работать), dev-админ, скрипты клиента, сброс кеша. Логин и пароль dev-админа после `CUser::Update` сверяются с базой: если обработчик `OnBeforeUserUpdate` клиента вырезал поле, оно пишется напрямую, а отчёт показывает логин из базы |
| Проверка утечек | REGEXP по текстовым колонкам: e-mail и телефоны, которые остались; если REGEXP в базе не справился — та же регулярка в PHP по последним строкам. `leak_scan`: `quick` (по умолчанию) — только колонки, которые правила не обрабатывали (и колонки с битыми сериализованными значениями), по последним `leak_quick_rows` строкам (20 000); `full` — все колонки целиком; `false` — без проверки. Режим и время — в отчёте. В режиме dict — ещё и имена людей в последних 300 строках каждой таблицы, с готовыми строками правил для скрипта клиента |

**Как устроены замены:**
- ID, суммы, даты, стадии и связи остаются, поэтому логика кейса сохраняется.
- Замены детерминированы внутри одного прогона: один и тот же телефон у лида и контакта станет одним и тем же фейком, и дубли останутся видны.
- Пол сохраняется: Мария станет Анной Ивановой.
- Двойник никогда не совпадает с оригиналом, даже если настоящее имя есть в наших списках: Иванов не станет Ивановым.
- Соль случайная, после прогона она нигде не хранится, поэтому замену нельзя обратить.

**Свободный текст** (комментарии, переписка, письма, названия сделок и лидов) обрабатывается в одном из трёх режимов:
- **dict** (по умолчанию) — текст остаётся, люди заменяются. Словарь собирается из ФИО самой базы: пользователи, контакты, лиды, реквизиты, соцсети. Каждый человек получает того же двойника, что и в карточке, и в том же падеже: «звонил Петрову» → «звонил Смирнову». Кроме людей заменяются e-mail, телефоны, ИНН физлиц, СНИЛС, карты, паспорта и адреса. Номера заказов, тендеров, суммы и даты остаются, поэтому по тексту можно разбирать задачи;
- **strict** — текст заменяется целиком на «[скрыто, N симв.]». Это надёжнее всего, но читать такой текст нельзя;
- **scrub** — заменяются только e-mail и телефоны, имена остаются. Нужен MySQL 8+ или MariaDB 10.0.5+.

Режим выбирается при обработке и запоминается в профиле клиента.

**Режим dict — это псевдонимизация, а не обезличивание.** Отчёт и главная так и пишут: «псевдонимизирована». Что может остаться:
- имя, которого нет в карточках базы и нет в списках частых имён, — например, человек, который упоминается только в переписке;
- редкая форма имени или опечатка;
- имя латиницей в косвенной форме: латиница находится только в точности как в карточке. Слово из трёх частей и больше через дефис («из-за-того-что», слаги ссылок) именем не считается, двойная фамилия — ровно две части;
- юрлицо вместе с должностью: «директор ООО Ромашка» указывает на конкретного человека, даже если его имя заменено;
- настоящее имя, которое совпало с именем из наших списков двойников. Проверка утечек такие слова не считает, потому что не отличает их от уже заменённых.

Если такие копии нельзя отдавать даже ИИ-ассистенту, выбирайте strict.

**Как dict устроен.** Пока идёт обработка, словарь лежит во временной таблице `zz_devrestore_dict`: в ней хеши основ ФИО с солью и двойники, самих имён нет. В конце таблица удаляется, а журнал запросов `performance_schema` очищается. Если обработку прервать, таблицу удалит кнопка «Сбросить», а главная о ней напомнит.

Текст чистится в PHP построчно, порциями около 2 МБ. Таблицы больше `clean_max_rows` строк (по умолчанию 500 000) чистить так слишком долго, их текст заменяется целиком, как в strict; отчёт перечисляет такие таблицы. Колонки-копии (`BODY_HTML` писем, `POST_MESSAGE_HTML` форумов и т. п.) тоже заменяются целиком: чистить одно и то же дважды незачем, а HTML чистится хуже.

`single_surname` в `config.php` (по умолчанию включено): одиночная фамилия из словаря («звонок Иванову») тоже заменяется. Выключите, если в текстах клиента много слов, совпадающих с фамилиями.

**Компании.** По умолчанию (`companies = individuals`) заменяются ИП, КФХ и физлица: название с «ИП …», компания и реквизит с ИНН из 12 цифр. Названия юрлиц остаются: для разбора задач «ООО Ромашка» полезнее, чем «Компания 3F2A1».

Что считать юрлицом, зависит от режима:
- в strict и scrub — только название, которое начинается с формы собственности (ООО, АО, ПАО, ГУП, МБУ…), со слов «Общество», «Акционерное» и т. п. или с кавычек. Всё остальное («Иванов Иван Иванович» без «ИП») заменяется;
- в dict название чистится словарём: люди в нём заменяются, остальное остаётся.

Режим `all` заменяет все названия, как в v1.

**Номера документов и счетов** (паспорт, ИНН, счёт) заменяются случайно, без хеша. Иначе короткий номер можно было бы подобрать перебором. ИНН из 10 цифр (юрлица) в режиме individuals остаётся.

**Пользовательские поля** распознаются по коду, подписи из `b_user_field_lang` и типу:
- поля Б24 вида `UF_CRM_1612345678` с подписью «Паспорт» станут цифрами, с подписью «Телефон» — телефоном;
- «Количество адресов» — не адрес, а «Карточка склада» — не номер карты: слабые признаки в подписи не срабатывают;
- нераспознанные строковые поля CRM и пользователей чистятся как текст (в режиме dict — по словарю);
- множественные значения хранятся в `b_utm_*`, а у смарт-процессов, RPA и highload-блоков — в своей таблице `<таблица сущности>_<поле>`. Обрабатываются там, а сериализованная копия в основной таблице очищается;
- строковые поля RPA (`RPA_*`) без признаков в коде и подписи чистятся как текст, так же как поля CRM.

Страница **«Поля клиента»** (ссылка на главной) показывает все строковые пользовательские поля: заполненность, форму значений (буквы → а/А, цифры → 9, сами значения не показываются) и сигналы: e-mail, телефон, документ, похоже на имя. Для каждого поля можно выбрать:
- **авто** — решение по коду и подписи;
- **оставить** — значение остаётся, вычищаются только e-mail, телефоны и номера документов. Подходит для служебных кодов;
- **чистить** — как текст;
- **заменить целиком**.

Решения хранятся в профиле клиента (`profiles.json`, ключ `uf`) и применяются при следующей обработке. Новые поля, которых не было в прошлый раз, перечислит отчёт. `uf_keep` в скрипте клиента продолжает работать и значит «оставить».

**Секреты, которые нужны на копии.** `options_keep` в скрипте клиента перечисляет опции `MODULE_ID/NAME` (точное совпадение, без масок, регистр не важен), которые шаг «Секреты» в `b_option` и `b_option_site` не стирает: например, `'options_keep' => ['vendor.api/API_KEY']`, чтобы вручную прогнать на копии несколько запросов к платному API. Значение остаётся прежним, с прода. Списки нескольких выбранных скриптов объединяются. В отчёте у шага «Секреты» каждый раз видно «оставлено по скрипту клиента: …» — только имена; имя, которого нет среди найденных секретов, отчёт называет отдельно. Секреты в колонках, `b_sale_bizval` и SMS-провайдеры `options_keep` не касается. Оставленный ключ безопасен, только пока агенты выключены: иначе модуль сам пойдёт с ним в API прода.

**Сброс входа.** После заливки браузер держит cookie прежней копии: страница открывается, а AJAX отклоняется по токену защиты (пустые поля в карточках CRM, не грузятся расширения), и сервер на каждый запрос заводит новую сессию. Поэтому в конце обработки:
- на сервере меняется `main/server_uniq_id`: подпись сессии считается от него, и ядро само уничтожит любую сессию прежней копии на первом хите. Файлы сессий не удаляются — каталог сессий PHP общий для всех сайтов сервера;
- ответ, который приносит отчёт, стирает в браузере cookie сессии и cookie Битрикс (префикс `cookie_name` сайта и любые `BITRIX_SM*`) — и без домена, и на домен хоста; по https ещё и `Clear-Site-Data: "cookies"`. Со страницы https нельзя стереть cookie, поставленные по http, и наоборот: их подстрахует сброс сессий на сервере;
- dev-админ больше не входит автоматически — на странице отчёта кнопка «Войти на портал». Если портал открыт и по http, и по https, войдите в том протоколе, в котором работаете.

Ключ доступа devrestore (`dr_key`) по http не стирается; по https `Clear-Site-Data` сотрёт и его — на тестовом сервере ключ при следующем открытии придётся ввести заново.

**Просмотр документов Диска.** Шаг «Секреты» стирает ключи облачного редактора (`disk_onlyoffice_b24_secretKey`, `disk_boards_b24_secretKey`): они привязаны к домену прода. Тогда просмотр документов переключается на встроенный (`default_viewer_service = bitrix`, для досок — пусто), иначе ядро сделает это само на первом хите и покажет админу баннер «выбран недоступный вариант». Если ключи оставлены через `options_keep`, выбор не трогается.

**Правила в скриптах клиента.** Метод `text` в правиле значит «свободный текст по режиму»: в dict он чистится словарём, в strict заменяется целиком. Метод `clean` всегда значит «чистить словарём». Если словаря нет (режим strict или scrub), `clean` работает как `text`.

В словарь попадают только записи с именем и фамилией, без цифр, `@` и пробелов. Одиночные NAME или LAST_NAME лида («Тендер», «Бухгалтерия») — обычно мусор, и иначе слово «Тендер» в названиях сделок стало бы фамилией.

Словарём чистится только то, что можно обновить построчно: таблица с числовым ключом и правило без JOIN. В остальных случаях в режиме dict (текст внутри `case`/`expr` скрипта, таблица без числового ключа) из текста вычищаются только e-mail и телефоны, а имена остаются. Такие колонки покажет проверка имён.

**Журнал и задания бизнес-процессов** (отдельная группа, её можно снять галкой) не удаляются, а чистятся: на копии это главный источник для расследований — какое действие что записало, кто что согласовал. В `b_bp_tracking` чистится текст записи `ACTION_NOTE`; заголовок и служебное имя действия (`ACTION_TITLE`, `ACTION_NAME`) берутся из шаблона и остаются. В `b_bp_task` название и описание задания чистятся как текст, а `DOCUMENT_NAME` (название сделки или элемента на момент задания) — как заголовок: в dict он получает те же замены, что и TITLE самой сделки. Остальные логи (`b_event_log` и др.) по-прежнему очищаются целиком.

**Колонки с уникальным ключом.** Если колонка входит в PRIMARY или UNIQUE (в том числе составной), одинаковая подмена упрётся в ключ: пустую строку получит одна запись, а остальные останутся с исходным значением. Поэтому в такие колонки `secret`, `empty` и `null` (для NOT NULL) пишут хеш исходного значения с солью той же длины (не короче 16 и не длиннее колонки), а `email` и `phone` — значение от первичного ключа. Если конфликт всё же случился, шаг завершается ошибкой с числом строк, оставшихся с исходным значением.

**Таблицы, которых нет.** Правило на несуществующую таблицу пропускается. Отчёт перечисляет такие таблицы отдельной строкой. Обычно это значит, что модуль не установлен, но если модуль есть, имя таблицы в правиле неверное — это пробел, о нём стоит сообщить.

**Смарт-процессы без типа.** Таблицы `b_crm_dynamic_items_N`, для которых в `b_crm_dynamic_type` нет записи (тип удалён, данные остались), очищаются целиком вместе с таблицами их множественных полей: открыть их в интерфейсе нельзя, а пользовательских полей в `b_user_field` у них уже нет, так что правила их не видят. Если по `b_crm_dynamic_type` не понять, какие таблицы живые (нет колонок `TABLE_NAME` и `ENTITY_TYPE_ID`), ничего не очищается.

**Сериализованное и JSON.** Методы `ser_text` и `json_text` (`b_crm_timeline.SETTINGS`, `b_crm_act.SETTINGS` и `PROVIDER_PARAMS`, `b_crm_button.SETTINGS`, `b_calendar_event.MEETING`, `b_bp_task.PARAMETERS`, `b_im_message_param.PARAM_JSON`, `b_forum_message.SERVICE_DATA`, `b_landing_history.ACTION_PARAMS`) чистят значение в PHP построчно и во всех режимах:
- значение распаковывается (`unserialize` без классов или `json_decode` в объекты, чтобы `{}` не стал `[]`). Если не получилось одним способом, пробуется другой: формат определяется по значению, метод — лишь подсказка;
- строки внутри чистятся по режиму: в dict — по словарю людей, в strict и scrub — только контакты и документы, как поле «оставить». Ключи не трогаются. Строки-коды и ссылки (`lead_12`, `CRM_DEAL`, `/crm/deal/details/5/`, `https://…`) — только контакты. Сериализованное или JSON внутри строки чистится как структура;
- значение упаковывается обратно: `serialize` или `json_encode` с теми флагами, которыми записан исходник (экранирование `\u`, `\/`, HEX-флаги Bitrix);
- если ничего не изменилось, строка не пишется;
- битое не трогается: не распаковалось, упаковка без изменений не даёт исходник байт-в-байт (хвост после значения, большое целое в JSON, пробелы и переносы), упакованное не помещается в колонку. Отчёт называет такие колонки с числом строк и первой строкой, а проверка утечек покажет, что в них осталось.

Внутрь объектов классов в сериализованном (`O:…`) чистка не заходит: они упаковываются обратно как были. Таблица без числового первичного ключа не чистится, отчёт называет её колонку. В dict таблица больше `clean_max_rows` чистится внутри только от контактов и документов, отчёт это отмечает.

**Чего обезличивание не касается:**
- файлы в `/upload` (сканы, договоры, вложения) — закройте их от ИИ;
- `b_user_option.VALUE` (настройки интерфейса, люди там редки, а формат у модулей разный) и состояние бизнес-процессов: `b_bp_workflow_state.STATE_PARAMETERS` (строковый ключ) и `b_bp_workflow_instance.WORKFLOW` (граф объектов). Остатки в них покажет проверка утечек;
- имена папок на Диске.

**Соль и её следы.** Соль случайная и живёт только во время обработки. В задачах вместо неё метка, а сама соль подставляется при выполнении запроса. Журнал и отчёт соль не содержат. В файле состояния она лежит до отметки в базе, потому что нужна между шагами, а потом удаляется, даже если следующий шаг ядра упадёт.

Что делает скрипт:
- для своих соединений выключает slow log;
- в конце очищает историю запросов `performance_schema`, а если на это нет прав, пишет об этом в отчёте.

Вне контроля скрипта остаются general log и binlog. Если они включены, отчёт предупредит. В MySQL 8 binlog включён по умолчанию, и в нём лежит весь исходный дамп прода из восстановления. На машине разработчика после обработки выполните `RESET MASTER`.

**Проверка утечек** ищет e-mail и телефоны во всех текстовых колонках. Телефоны распознаются и в тексте, и в проверке: с `+7` или `8`, без разделителей (11 цифр) и мобильные без кода страны, но с разделителями («912 345-67-89»). Десятизначное число без разделителей телефоном не считается: это может быть номер заказа. Цифры, к которым вплотную примыкает латинская буква, тоже: 11 цифр внутри hex-ID, UUID и хешей — не телефон. Колонки идентификаторов и хешей (`*_ID`, `UUID`, `GUID`, `HASH`, `ETAG`, `XML_ID`, `CODE`, `DIGEST`…) проверяются только на e-mail. Если REGEXP в базе не справился с колонкой (длинный текст, лимит регулярок MySQL), она проверяется той же регуляркой в PHP по последним 2000 строкам, а отчёт это называет; колонки, которые не удалось проверить вовсе, перечислены на виду, а не под спойлером. Таблицы больше `leak_scan_max_rows` строк проверяются выборочно, по последним 200 000 записям. В режиме dict она дополнительно ищет имена людей в последних 300 строках каждой таблицы. Слово, которое есть в справочниках самой базы (названия статусов CRM, значения списков инфоблоков, населённые пункты), именем не считается: «Кимры» — город, даже если в базе есть человек с такой фамилией. Строки внутри сериализованных значений проверяются тоже, но правило `clean` для такой колонки сломает формат, поэтому готовой строки для неё нет: для сериализованного и JSON есть методы `ser_text` и `json_text`. Для остального найденного отчёт даёт замаскированный пример и готовую строку правила:

```php
['table' => 'zz_legacy_people', 'set' => ['note' => 'clean']],
```

Её можно вставить в `anonymize` скрипта клиента, после чего базу нужно обработать заново.

**Отложено:**
- постоянная соль в профиле: одинаковые двойники от копии к копии, чтобы ИИ-ассистент узнавал «того же» клиента;
- сериализованное в таблицах со строковым ключом (`b_bp_workflow_state`) и внутри объектов классов, blob `b_bp_workflow_instance.WORKFLOW`;
- таблица инициалов («И. И. Иванов») и пары имён в нижнем регистре;
- `full_name`-поля (одной строкой «Фамилия Имя Отчество») как источник словаря;
- соль, которая создаётся и хранится только в MySQL (`@s`), чтобы её не было ни в файле состояния, ни в тексте запросов;
- поиск ИНН-12, СНИЛС, карт и паспортов в проверке утечек (в самом тексте они уже заменяются);
- числовые HTML-сущности («&#1048;ван») в письмах и описаниях дел;
- компактный словарь (бинарные ключи) для баз с сотнями тысяч людей;
- маскировка домена e-mail в примерах утечек: личный домен тоже указывает на человека;
- порог `clean_max_rows` по таблице, а не один на всех: на крупной базе под него попадают `b_im_message` и `b_event_log`, и в dict чаты заменяются целиком;
- содержимое файлов `/upload` не обезличивается (меняются только имена) — предупреждение в отчёте, если архив прода пришёл с upload, или опция-заглушка;
- проверить, что после обработки в `b_user_device_login` не остаются IP и устройства.

## Защита

- Папка профилей должна существовать заранее и лежать вне корня сайта.
- Хост должен быть в `allowed_hosts`. По умолчанию это `localhost` и `*.local`, `*.loc`, `*.test`, `*.localhost`.
- Если открыть не с 127.0.0.1, нужен `access_key`. Запрос через прокси (заголовки `X-Forwarded-For` и т. п.) тоже считается удалённым.
- На тестовом сервере файл в конце удаляет себя (`self_delete = 'auto'`). Сайт в Docker на своей машине приходит не с 127.0.0.1 — поставьте `'self_delete' => false`.
- `restore.php` после обработки удаляется всегда.
- Подготовка требует ввести текущий домен и проверяет CSRF.
- Обработка запрещена, если любой домен из базы (`server_name`, домены сайтов, с `www.` и без) совпадает с текущим хостом, а отметки обезличивания нет. Хост, который записан в профилях как боевой, блокируется сразу.
- Возврат из restore.php проходит по одноразовому токену.

## Папка профилей

Папка профилей — `.devrestore` рядом с корнем сайта: для `/var/www/client.local/public` это `/var/www/client.local/.devrestore`. Её нужно создать один раз руками — это и есть разрешение запускать devrestore на этой машине; `config.php` внутри скрипт создаст сам.

Почему не внутри корня сайта: оттуда профили, журналы и состояние обработки были бы доступны из браузера, а при выкладке папка уехала бы на сервер вместе с сайтом. Папку внутри корня скрипт не принимает.

Одна общая папка на все проекты — по желанию. Переопределения проверяются по порядку, берётся первое, где папка существует:
1. константа `DR_HOME` в начале `devrestore.php` (в коде по умолчанию пусто);
2. переменная окружения `DEVRESTORE_HOME`;
3. `.devrestore` рядом с корнем сайта.

В папку профилей может заглянуть ИИ-агент, если она лежит в папке проекта. Поэтому в `state/`, `logs/` и отчёте нет ни соли, ни пароля dev-админа, а примеры утечек замаскированы. Ключ `delight.mcp` хранится в `state/` только между подготовкой и обработкой.

```
.devrestore/
  config.php        хосты, ключ, dev-админ, режим текста, исключения агентов, модули разработки
  profiles.json     боевой домен → выбранные скрипты, режим, снятые группы (пишет скрипт)
  scripts/*.php     скрипты клиентов: доп. правила обезличивания, SQL, действия в ядре
  state/, logs/     состояние текущей обработки и журнал logs/devrestore-ГГГГ-ММ.txt (без соли и без ПДн)
```

Образец скрипта клиента — `devrestore-home/scripts/_example.php` в репозитории: скопируйте его в `scripts/` своей папки профилей под именем клиента. Скрипты клиентов в репозиторий не попадают (см. `.gitignore`).

На тестовый сервер можно приехать одним файлом: задайте в начале `devrestore.php` константы `DR_ACCESS_KEY` и `DR_ALLOWED_HOSTS`.

## Тесты

**Сквозной тест** `tests/e2e.php` поднимает сайт-заглушку с ядром из `tests/stub`, синтетическую схему с краевыми случаями и `php -S`.

Краевые случаи:
- таблица в cp1251;
- ID от 10⁹ с дырами;
- NULL и пустые строки;
- составной PK;
- множественные UF;
- 25 000 сообщений и 3 000 записей таймлайна (чистка пачками);
- чужая таблица в базе;
- однофамильцы с несклоняемой фамилией;
- ИП без имени в названии;
- мусор в ФИО лидов.

Тест проходит весь путь:
1. подготовка → «восстановление»: многотомный дамп в формате резервной копии Битрикс грузится клиентом mysql в фоне — сначала с ошибкой (всё отключено, «заново»), затем целиком (пропуск данных, отключение агентов по ходу импорта, удаление файла с паролем, убитый процесс) → обработка → проверки SELECT-ами;
2. повтор → автозапуск без клиента mysql (дамп грузит restore.php) → режим scrub;
3. страница «Поля клиента» → режим dict (паритет двойников в тексте и в карточках, компании, UF, полная проверка утечек и проверка имён, следы соли);
4. брошенный словарь → «Сбросить»;
5. отказы защиты.

Нужна одноразовая MySQL или MariaDB с пользователем root без пароля:

```bash
php tests/e2e.php --port=3399 --name=mysql80
```

```bash
php tests/e2e.php --port=3398 --name=maria --php=<путь к php 7.4>
```

`--src=<копия devrestore.php>` прогоняет тест на копии: так проверяются мутанты.

**Юнит-тест** `tests/unit-names.php` проверяет склонение, разбор ФИО и чистку текста без базы: падежи, инициалы, однофамильцы, телефоны, документы, а также то, что заменяться не должно (номера, гео, названия организаций). Он тоже принимает `--src`.

```bash
php tests/unit-names.php
```

Где проверено:
- e2e, 208 проверок: MySQL 8.0.44 (веб-сервер на PHP 8.4 и 7.4 с OPcache) и MariaDB 10.11 (PHP 7.4 и 8.4), клиенты mysql и mariadb из поставки сервера;
- юнит-тест, 338 проверок: PHP 7.4 и 8.4.

Ключевые проверки сами проверены мутантами: в копию вносится поломка, и соответствующая проверка обязана упасть. Так сделано для 115 защит, в том числе для каждой правки после ревью и аудита.

Заглушка ядра не заменяет настоящий Битрикс: первый прогон на реальной копии смотрите по отчёту и проверке утечек.

Однофайловость — требование задачи, поэтому `devrestore.php` больше обычного предела 600 строк.
