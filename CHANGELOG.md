# Изменения

## 2.9.1 — агенты прода не оживают во время и после сбоя импорта

- Таблицы агентов, опций, очереди писем, вебхуков и почтовых ящиков отключаются по ходу импорта. Как только строки такой таблицы кончились в дампе, в поток уходят COMMIT и метка. Когда клиент до метки дошёл, таблица отключается своим соединением. Окно, в котором агенты прода видны активными, — секунды, а не весь импорт. Шаг после импорта остаётся страховкой.
- Импорт упал (клиент mysql вернул ошибку) — агенты, очередь писем, вебхуки и ящики всё равно отключаются, в журнале строка «после ошибки отключены…».
- Фоновый процесс убит (например, вместе с php-cgi) — отключает страница импорта, когда видит, что процесс прервался.

## 2.9.0 — быстрая заливка

- **Импорт дампа клиентом mysql.** restore.php только распаковывает архив: четвёртая вставка в начало шага 3 передаёт дамп devrestore, а тот грузит его в фоне (`php devrestore.php --dr-import=<токен>`) потоком в клиент mysql, включая тома `.sql.1`, `.sql.2`…. Клиент ищется так: `mysql_bin` в `config.php`, затем `bin/` рядом с сервером (`@@basedir`), затем `PATH`. PHP для командной строки — `php_bin` или рядом с PHP веб-сервера. Не нашлось — форма называет причину, дамп грузит restore.php, как раньше. `mysql_bin = false` выключает быстрый импорт, галка в форме — на один раз.
- Как restore.php: выполняется `_after_connect.sql`, выключена проверка внешних ключей, `sql_mode` пустой, повтор строки пропускается (`INSERT IGNORE`). Проверка уникальности остаётся включённой: с ней выключенной MariaDB 10.11 при повторе строки в дампе молча теряла уже вставленные строки транзакции.
- Пароль базы — во временном файле параметров (`--defaults-extra-file`, 0600). Файл удаляется, когда клиент ответил на первый запрос: чужие соединения с тем же сервером на это не влияют.
- Агенты, очередь писем, вебхуки и почтовые ящики отключаются тем же процессом сразу после импорта. Там же — то, что шаг 4 restore.php делает для копии на другом хосте: корень сайтов, CDN Битрикс, ограничение хостов.
- Страница импорта показывает ход, после окончания сама переходит к обработке. Второй процесс не стартует (блокировка). Если процесс упал — ошибка и кнопка «Начать импорт заново». Ссылка на обработку до конца импорта возвращает на импорт.
- **Пропуск данных** (`import_skip_truncated`, по умолчанию включён): строки таблиц, которые обработка очищает целиком, не загружаются, структура создаётся. Список — из тех же правил, кроме групп, выключенных по умолчанию.
- **Проверка утечек: режимы.** `leak_scan = 'quick'` (по умолчанию) — только колонки, которые правила не обрабатывали (и колонки с битыми сериализованными значениями), по последним `leak_quick_rows` строкам (20 000); `'full'` — все колонки целиком; `false` — без проверки. Режим — в строке результата.
- **Время в отчёте:** «Время обработки», «Импорт» (способ, время, размер, тома, пропущенные данные; для restore.php — время от подготовки до возврата и почему не клиентом mysql), время этапов (обезличивание, проверка на утечки, завершение) и пять самых долгих шагов.

## 2.8.0 — сериализованное и JSON

- Новые методы `ser_text` и `json_text`: значение распаковывается, строки внутри чистятся, значение упаковывается обратно. Работают во всех режимах: в dict — по словарю людей, в strict и scrub — только контакты и документы. Ключи не трогаются, коды и ссылки — только контакты. Формат определяется по значению, вложенное сериализованное или JSON чистится как структура.
- JSON упаковывается с флагами исходника (экранирование `\u` и `\/`, HEX-флаги Bitrix), пустой объект `{}` остаётся объектом.
- Если ничего не изменилось, строка не пишется. Битое не трогается: не распаковалось, упаковка не воспроизводит исходник байт-в-байт, не помещается в колонку. Отчёт называет такие колонки с числом строк, проверка утечек показывает остатки.
- Правила: `b_crm_timeline.SETTINGS`, `b_crm_act.SETTINGS` и `PROVIDER_PARAMS`, `b_crm_button.SETTINGS`, `b_calendar_event.MEETING`, `b_bp_task.PARAMETERS`, `b_im_message_param.PARAM_JSON`, `b_forum_message.SERVICE_DATA`, `b_landing_history.ACTION_PARAMS`.
- Не трогаются: `b_user_option.VALUE`, `b_bp_workflow_state.STATE_PARAMETERS` (строковый ключ), `b_bp_workflow_instance.WORKFLOW`, объекты классов внутри сериализованного. Колонку в таблице без числового ключа отчёт называет.

## 2.7.0 — вход после заливки и просмотр документов

- Сброс входа прежней копии. Dev-настройки ставят новый `main/server_uniq_id`: подпись сессии считается от него, и ядро уничтожит любую сессию прежней копии на первом хите. Ответ, который приносит отчёт, стирает cookie сессии и Битрикс (без домена и на домен хоста; по https ещё и `Clear-Site-Data: "cookies"`). Ключ доступа devrestore по http не трогается. Файлы сессий не удаляются — каталог общий для всех сайтов сервера.
- Dev-админ больше не входит автоматически: отчёт показывает логин и пароль, кнопку «Войти на портал» и подсказку про http и https.
- Просмотр документов Диска: если шаг «Секреты» стёр ключ облачного редактора, просмотр переключается на встроенный (`default_viewer_service = bitrix`, доски — пусто), строка в отчёте. Ключи из `options_keep` — выбор не трогается. Без этого ядро само переключало просмотр и показывало админу баннер.

## 2.6.0 — итоги первой заливки на реальной базе Б24

**Обязательные исправления**
- Dev-админ: после `CUser::Update` логин, активность и пароль сверяются с базой. Если обработчик `OnBeforeUserUpdate` клиента вырезал поле (а `Update` всё равно вернул успех), оно пишется напрямую. Отчёт показывает логин из базы, а если записать не удалось — фактический логин и ошибку.
- Колонки с уникальным ключом (PRIMARY/UNIQUE, в том числе составным): `secret`, `empty` и `null` для NOT NULL пишут хеш исходного значения с солью той же длины, а не пустую строку. Раньше пустое значение получала одна запись, а остальные оставались с настоящими токенами. Если конфликт ключа всё же случился, шаг завершается ошибкой с числом строк, оставшихся с исходным значением.
- Токены CalDAV (`b_dav_tokens`) и блокировки документов Диска (`b_disk_object_lock`) очищаются вместе с сессиями.
- Адреса модуля location: правило на `b_location_addr_fld` (так таблица называется в ядре); старое имя `b_location_address_field` оставлено.
- Отчёт перечисляет таблицы из правил, которых нет в базе: «таблицы нет» больше не выглядит как «пусто».

**Новые правила**
- Смарт-процессы, тип которых удалён (нет записи в `b_crm_dynamic_type`), очищаются целиком вместе с таблицами их множественных полей.
- Множественные пользовательские поля смарт-процессов, RPA и highload-блоков в своих таблицах `<таблица>_<поле>` обрабатываются методом самого поля.
- Строковые поля RPA без признаков чистятся как текст, как поля CRM.
- Календарь: события (название, описание, место, поисковый текст), календари, идентификаторы внешних календарей, данные синхронизации, подключения CalDAV.
- Телефония: номера сотрудников (`b_voximplant_phone`), поисковый индекс статистики, номер в чатах звонков — тем же хешем, что в статистике.
- Задачи: чек-листы (и в шаблонах), результаты, история изменений (только строки со словами), `b_tasks_effective`, метки; `b_tasks_scorer_event` очищается.
- Корзина (`b_recyclebin*`) очищается.
- Прочее: заметки таймлайна, результаты звонков, должность контакта, блоги, форумы (последний автор), отчёты, рабочие отчёты, история ИИ, пароли приложений (комментарий), вкладки боковой панели, события календаря в чатах, личные хранилища Диска, рассылки, участники подписания.
- В чистке текста e-mail распознаётся с любыми буквами: адреса на `.рф` и с кириллической буквой в домене раньше проходили мимо.

**Проверка утечек**
- Регулярки телефона с границами «не цифра и не латинская буква»: 11 цифр внутри hex-ID, UUID, хешей и ИНН-12 больше не считаются телефоном.
- Колонки идентификаторов и хешей (`*_ID`, `UUID`, `HASH`, `ETAG`, `XML_ID`, `CODE`…) проверяются только на e-mail.
- Если REGEXP в базе не справился с колонкой, она проверяется той же регуляркой в PHP по последним 2000 строкам; непроверенные колонки отчёт показывает на виду.
- Поиск имён не считает именем слово из справочников самой базы: статусов CRM, списков инфоблоков, местоположений. Расширен список обычных слов.

**Прочее**
- Версия 2.6.0 на экране и в опции `devrestore/info`.
- Журнал — `logs/devrestore-ГГГГ-ММ.txt` (открывается в файловом менеджере Битрикса).

## 2.5 — папка профилей рядом с проектом
`DR_HOME` в коде пуст. Папка профилей по умолчанию — `.devrestore` рядом с корнем сайта. Переопределения: `DR_HOME` и переменная окружения `DEVRESTORE_HOME`.

## 2.4 — самообновление restore.php
Третья вставка выключает самообновление restore.php, которое стирало вставки devrestore. Записанный файл перечитывается. Главная предупреждает о restore.php без вставок.

## 2.3 — память в разборе имён
Слова из многих частей через дефис больше не взрывают перебор вариантов: двойная фамилия — ровно две части, латиница — точное совпадение.

## 2.2 — журнал бизнес-процессов
Журнал и задания БП чистятся отдельной группой, а не удаляются.

## 2.1 — options_keep
Скрипт клиента может оставить нужные на копии опции-секреты.

## 2.0 — словарь людей
Режим dict (текст остаётся, люди заменяются двойниками в том же падеже), пользовательские поля по содержимому и страница «Поля клиента», юрлица сохраняются, проверка утечек по именам.

## 1.0.0
Восстановление через restore.php, обезличивание, отключение внешних действий, dev-настройки, скрипты клиента.
